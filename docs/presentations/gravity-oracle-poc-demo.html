Oracle PoC briefing

External facts become contract state on Gravity.

This PoC shows two rails: finalized Polymarket-style settlements and HIP3 price observations flowing through validator consensus into G-native contracts.

sourceType=6 Polygon CTF settlement mirror for match-market resolution.
sourceType=3 HIP3 price feed for NVDA / GOOGL-style contract consumption.
JWK bytes rail Reuse existing unsupported-JWK consensus transport.

One Rail, Two Products

Relayer code fetches and canonicalizes. Validators agree on bytes. Execution records through NativeOracle. Product contracts consume resolver state.

External source Finalized CTF settlement or HIP3 price observation.
gravity-reth Source adapter fetches and normalizes payloads.
Canonical bytes Deterministic ABI payload for validator agreement.
JWK consensus Unsupported-JWK path transports agreed bytes.
NativeOracle Records sourceType, sourceId, nonce, block, payload.
Resolver / Product Settlement resolver, price resolver, market, PerpDex.
The validator adapter should not hide product policy. BBO, local mid, TWAP, funding, and risk belong in PerpDex or a versioned resolver policy.

Track A: Polymarket-like Settlement

Mirror finalized settlement truth from Polygon CTF into a G-native match market. We do not clone Polymarket UI or its order book.

V1 Direct-Fit Case

  • One reviewed Polymarket CTF condition.
  • Finalized Polygon ConditionResolution.
  • Explicit slot-to-outcome mapping.
  • Gravity market rules frozen as specHash.
  • Contract rejects missing or ambiguous payout.
sourceType=6 mirrorId conditionId slotToOutcome

Not Automatic Yet

  • Multiple binary markets composed into one 3-way market.
  • Scalar or partial payout vectors.
  • Disputed, cancelled, postponed, or ambiguous markets.
  • Markets without a reviewed rules snapshot.
  • Automatic discovery from UI or Gamma API.

Gaps Before Production

  • Real Polygon historical replay against selected Polymarket conditions.
  • Market metadata registry and rulesHash / specHash builder.
  • Multi-condition settlement mode for multiple binary markets.
  • Provider allowlist and governance config.
  • Dynamic request watcher with finality gate and watermark backfill.
  • Retry, expiry, Pending, Unknown, and Expired response model.
  • Multi-validator heterogeneous source config tests.
  • PerpDex BBO, mid, TWAP, funding, and risk integration.

Q&A

Short answers for the questions people will almost certainly ask.

Can we mirror any Polymarket match?

No automatic blanket mirror yet. V1 can mirror direct-fit finalized CTF conditions. Complex UI markets need metadata/rules registry and more settlement modes.

Is HIP3 price the same as official Nasdaq spot?

No. Treat xyz:NVDA and xyz:GOOGL as HIP3/perp-derived price observations. Production feed policy must define the field and source semantics.

Who calculates BBO or mid?

The PerpDex or a versioned resolver policy. Validators should fetch deterministic observations, not hide product-specific market logic.

Why reuse the unsupported-JWK path?

The existing validator consensus path can already agree on bytes payloads and write them into execution. Reusing it reduces consensus-core change risk for this PoC.

Does dynamic request work now?

The current PoC is mainly epoch-config long-running feeds. Dynamic one-off requests need a watcher with finality gate, watermark/backfill, deadline/expiry, typed responses, retry, and request/config/payload hashes.
